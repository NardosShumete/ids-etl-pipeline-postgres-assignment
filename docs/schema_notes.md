# PostgreSQL Schema Design and Normalization Documentation

**Project:** Intrusion Detection System Data Pipeline and ETL Process  
**Dataset:** UNB CIC-IDS-2017 (2.83M Flow Records, 8 CSV Files, 79 Columns)  
**Target Database:** PostgreSQL 14+  
**Target Scenario:** Security Operations Center (SOC) / Network Operations Center (NOC) at an Ethiopian Internet Service Provider (e.g., Ethio Telecom) or National Commercial Bank  

---

## 1. Executive Summary & Business Scenario

In a major telecommunications network or national banking backbone, network operations teams monitor massive volumes of bidirectional traffic flows to protect critical infrastructure against cyber threats (including Distributed Denial of Service [DDoS], Port Scanning, Brute Force attacks, Web Injections, and Botnet command-and-control).

Storing raw, unnormalized network captures directly in a relational database introduces severe disk bloat, cache thrashing, and degraded query throughput. This document details the architectural choices, normalization steps (1NF through 3NF), vertical partitioning, data typing, and indexing strategy employed to store and analyze 2.83 million records from the CIC-IDS-2017 benchmark dataset in PostgreSQL.

---

## 2. Raw Dataset Characteristics and Limitations

The raw CIC-IDS-2017 dataset consists of 8 CSV files generated by `CICFlowMeter` from packet capture (`.pcap`) files across 5 working days:
- **Total Records:** Approximately 2,830,743 labeled network flows.
- **Raw Dimensionality:** 79 columns (78 numerical/statistical flow features + 1 string `Label` column).
- **Redundancies in Raw Format:**
  1. The string label (e.g., `"DoS Hulk"`, `"PortScan"`, `"BENIGN"`) is duplicated across all 2.83 million rows, consuming tens of megabytes of redundant text storage.
  2. The raw files lack metadata regarding capture lineage, file origin, and day-of-week context.
  3. Every record bundles basic connection identifiers (ports, durations, byte counts) together with 56 deep statistical variance and inter-arrival metrics that are rarely needed during routine firewall monitoring.

---

## 3. Database Normalization Strategy

To eliminate redundancy, maintain referential integrity, and maximize query efficiency, the relational model implements 3NF alongside performance-oriented vertical partitioning.

```
+--------------------+        +---------------------+
|    source_files    | 1    * |        flows        | 1    1 +---------------------+
|--------------------|--------|---------------------|--------|   flow_statistics   |
| id (PK)            |        | id (PK)             |        | flow_id (PK, FK)    |
| file_name          |        | source_file_id (FK) |        | fwd_pkt_len_max...  |
| capture_day        |        | attack_type_id (FK) |        | fwd_iat_total...    |
+--------------------+        | destination_port    |        +---------------------+
                              | flow_duration       |
+--------------------+        | ...core telemetry...|
|    attack_types    | 1    * +---------------------+
|--------------------|--------+
| id (PK)            |
| label (UK)         |
| category           |
| is_malicious       |
+--------------------+
```

### 3.1 First Normal Form (1NF)
- **Atomicity:** All attributes store single, atomic scalar values (integers, floats, booleans, strings). No composite structures, repeating groups, or delimited lists exist.
- **Unique Identification:** Every entity possesses a distinct primary key (`id` or `flow_id`).
- **Consistent Types:** Every column enforces strict PostgreSQL data types.

### 3.2 Second Normal Form (2NF)
- **Full Functional Dependency:** The tables use single-column surrogate primary keys (`id` in `source_files`, `attack_types`, `flows`, and `flow_id` in `flow_statistics`). Because no composite primary keys exist, no non-key attribute can have a partial dependency on a subset of a candidate key. All attributes depend entirely on the primary key.

### 3.3 Third Normal Form (3NF)
- **Elimination of Transitive Dependencies:** In the raw dataset, the attack label implicitly dictates whether the traffic is malicious and which broad attack family it belongs to (e.g., `Label = 'FTP-Patator'` implies `Category = 'Brute-Force'` and `is_malicious = TRUE`). 
- **Lookup Normalization (`attack_types`):** Storing `category` and `is_malicious` inside each flow record would create transitive dependencies (`flow_id -> label -> category`). We extracted attack categories into `attack_types` (15 discrete rows), replacing string labels in the 2.83M flow records with a 2-byte foreign key (`SMALLINT REFERENCES attack_types(id)`).
- **Lineage Normalization (`source_files`):** Instead of storing file paths or capture day names across millions of rows, file metadata is isolated in `source_files`, referenced via a 4-byte `INTEGER` foreign key.

## 4. Vertical Partitioning: `flows` vs. `flow_statistics`

A key architectural design in this schema is the **1:1 vertical partitioning** between `flows` and `flow_statistics`.

### Why Partition Vertically?
In PostgreSQL, table storage is managed in **8 KB shared buffer pages**:
- **Wide Row Overhead:** Storing all 79 columns in a single table results in an average row width exceeding 650 bytes. A standard 8 KB page can hold only ~11 to 12 rows. A sequential scan over 2.83 million wide rows requires reading roughly **240,000 pages (~1.9 GB)** from disk or memory.
- **Targeted Telemetry (`flows` table):** In 95% of SOC operational workflows (e.g., alert generation, port traffic volume analysis, DDoS detection, high-rate flag inspection), analysts query only 8 to 15 core columns: `destination_port`, `flow_duration`, `packet_count`, `byte_count`, and TCP flags (`SYN`, `RST`, `ACK`).
- **Partition Benefits:**
  - The partitioned `flows` table has an average row width of ~160 bytes, allowing **45+ rows per 8 KB page** (a **3.7x density improvement**).
  - Routine SOC queries read only ~62,000 pages instead of 240,000 pages, reducing disk I/O, cache misses, and memory footprint.
  - The deep statistical variance and subflow metrics (56 numeric columns) reside in `flow_statistics` and are joined via primary key `flow_id` only when performing deep forensic audits or training machine learning models.

## 5. PostgreSQL Data Type Sizing & Precision

Every column is typed to prevent data truncation while minimizing physical disk footprint:

| Column / Category | Data Type | Bytes | Justification |
| :--- | :--- | :--- | :--- |
| `flows.id` | `BIGSERIAL` | 8 | Primary key. A 4-byte `SERIAL` overflows at 2.14 billion rows; enterprise network logs easily exceed this threshold over months of continuous capture. |
| `attack_types.id` | `SMALLSERIAL` | 2 | Max value 32,767. More than sufficient for intrusion taxonomies (< 50 categories). |
| `flows.attack_type_id` | `SMALLINT` | 2 | Saves 2 bytes per row over `INTEGER` across 2.83M rows (~5.6 MB savings). |
| `flows.destination_port` | `INTEGER` | 4 | TCP/UDP ports span 0–65,535. PostgreSQL `SMALLINT` is signed (-32,768 to +32,767), so ports > 32,767 require `INTEGER` with a `CHECK (destination_port >= 0 AND destination_port <= 65535)`. |
| `flows.flow_duration` | `BIGINT` | 8 | Microseconds. Long sessions (e.g., > 35.7 minutes) exceed 2,147,483,647 microseconds, which overflows standard `INTEGER`. |
| Packet & Byte Totals | `BIGINT` | 8 | Volumetric DDoS floods generate billions of packets/bytes, exceeding 32-bit signed integers. |
| TCP Flag Counts | `SMALLINT` | 2 | Flag counters within a single flow rarely exceed small positive counts. |
| Rates & Statistical Moments | `DOUBLE PRECISION` | 8 | Required for 64-bit IEEE 754 floating-point accuracy (means, standard deviations, variances, inter-arrival times). |

## 6. Integrity and Domain Constraints

To enforce data quality at the database level and prevent corrupted network captures from entering the operational store:
1. **Domain CHECK Constraints:**
   - `destination_port >= 0 AND destination_port <= 65535`: Strictly enforces valid RFC 793 / RFC 768 port boundaries.
   - `flow_duration >= 0`: Time intervals in physical networks cannot be negative.
   - Packet and byte counts (`total_fwd_packets >= 0`, `total_length_of_fwd_packets >= 0`): Flow volumes are strictly non-negative.
   - Statistical metrics (`packet_length_variance >= 0`, `*_iat_min >= 0`): Prevents invalid negative mathematical variances.
2. **Referential Integrity (Foreign Keys):**
   - `flows.source_file_id REFERENCES source_files(id) ON DELETE CASCADE`: Deleting an audit file record cleans up associated flow telemetry.
   - `flows.attack_type_id REFERENCES attack_types(id) ON DELETE RESTRICT`: Prevents accidental deletion of attack definitions while flow records still depend on them.
   - `flow_statistics.flow_id REFERENCES flows(id) ON DELETE CASCADE`: Guarantees 1:1 synchronization; deleting a flow removes its detailed statistical row.
3. **NOT NULL Constraints:**
   - Enforced on all primary keys, foreign keys, destination ports, flow durations, and core packet totals.

## 7. Indexing Strategy and Bulk Loading Lifecycle

PostgreSQL maintains B-Tree indexes synchronously during `INSERT` statements. For a high-volume load of **2.83 million rows**:
- **Why Separate `02_indexes.sql`?** Inserting into a table with 4+ B-Tree indexes forces the database engine to perform random disk lookups, balance B-Tree leaves, and generate massive Write-Ahead Log (WAL) traffic for every batch.
- **Optimal Lifecycle:**
  1. Deploy tables and constraints (`01_schema.sql`).
  2. Bulk load data via PostgreSQL `COPY` command (sequential append, zero index maintenance).
  3. Deploy indexes (`02_indexes.sql`). Post-load index creation sorts data in memory (using `maintenance_work_mem`), producing fully compacted B-Tree pages with 0% fragmentation in a fraction of the time.

### Index Inventory and Justification

```sql
-- 1. Foreign Key acceleration for JOINs
CREATE INDEX idx_flows_attack_type_id ON flows (attack_type_id);
CREATE INDEX idx_flows_source_file_id ON flows (source_file_id);

-- 2. Port-based service filtering
CREATE INDEX idx_flows_destination_port ON flows (destination_port);

-- 3. Temporal/duration anomaly detection
CREATE INDEX idx_flows_duration ON flows (flow_duration);

-- 4. Composite Threat Hunting Index (Attack Category + Target Port)
CREATE INDEX idx_flows_attack_port ON flows (attack_type_id, destination_port);

-- 5. Dimension lookups
CREATE INDEX idx_attack_types_category ON attack_types (category);
CREATE INDEX idx_source_files_capture_day ON source_files (capture_day);
```

## 8. Threat Hunting & SOC Analytical Query Mapping

The designed schema directly facilitates common queries run by telecom and banking SOC analysts:

### Example A: Detecting Port Scanning Activity
```sql
SELECT 
    f.destination_port,
    COUNT(*) AS flow_count,
    COUNT(DISTINCT f.destination_port) AS unique_ports_targeted
FROM flows f
JOIN attack_types a ON f.attack_type_id = a.id
WHERE a.category = 'PortScan'
GROUP BY f.destination_port
ORDER BY flow_count DESC
LIMIT 10;
```

### Example B: Volumetric DDoS Traffic Analysis
```sql
SELECT 
    a.label AS attack_name,
    COUNT(f.id) AS total_flows,
    ROUND(SUM(f.total_length_of_fwd_packets + f.total_length_of_bwd_packets) / (1024.0 * 1024.0), 2) AS total_mbytes,
    ROUND(AVG(f.flow_bytes_per_s)::numeric, 2) AS avg_bytes_sec
FROM flows f
JOIN attack_types a ON f.attack_type_id = a.id
WHERE a.is_malicious = TRUE
GROUP BY a.label
ORDER BY total_flows DESC;
```
